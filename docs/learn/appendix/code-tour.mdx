# A tour of the code

<OneSentence>The chapters teach the ideas; this page walks you through the files that carry them, in an order where each stop only needs the ones before, with something to run at each one.</OneSentence>

Inkshelf is about 34,000 lines of Go in some fifty packages. Reading them in alphabetical order
would teach you little. This tour follows the parts of the site: read a part's chapters first,
then come here and open its files in the editor, in order. Each stop says what to look at and
gives a command to run (from the root of the repository), so you see the code work rather than
only read it.

Three **threads** cross the parts. Follow one end to end and you will have touched most of the
code:

1. **Start-up**: from `main` to the first screen.
2. **A page turn in an EPUB**: from a tap to the panel refreshing.
3. **A download**: from a tap on a book to `.pg4` files on the reader.

<Analogy icon="🗺️">A guided walk through a city. The chapters are the guidebook; this is the
route, with the stops, the order, and what to look at when you get there.</Analogy>

## Before you start

You need Go, and nothing else for the first stops. Run the app once, so you know what the code
is doing:

```sh
make emu-fake          # the app against a fake Komga, at http://localhost:8740
make test              # every test, on your computer
```

Two habits help along the way:

- **Read the package's doc first.** Most packages begin with a `doc.go` that teaches their
  domain. `go doc ./internal/shelf` prints it without opening an editor.
- **Run one test with `-v`.** A test is the smallest program that uses a function:
  `go test ./internal/naturalorder -run TestNaturalCompare -v`.

## Stop 0: the map

Read [The layer cake](/big-picture/layers), then the domain map in `CLAUDE.md` at the root of
the repository. It lists every package with one line on what it does. Keep it open: whenever a
stop names a package, find it on the map.

Then check the rule that holds it together yourself:

```sh
go list -deps ./internal/app/... ./internal/shelf | grep -E 'servers/(komga|mealie|calibreweb)'
```

It prints nothing: the app and the shelf never import a specific server.

**Notice:** `run` in `pocketbook/app.go` is the heart of the program. One goroutine, one
`select`: repaint requests call `app.Draw`, input wakes it and a timer polls the firmware, which ends in
`app.Key`, `app.Pointer` or `app.System`. Everything the app does starts from one of these
calls.

```sh
go doc ./internal/device/pocketbook
go test ./internal/device/pocketbook -run TestEventLoop -v
```

**Ask yourself:** `cmd/inkshelf` and `cmd/emulator` both call `app.New`. What is different
about what they pass it?

Now follow **thread 2**, a page turn, from the tap to the panel. Open each function in turn:

1. `reader.Screen.Command` (`internal/app/screens/reader/reader.go`) receives "next page".
2. `openbook.TurnPage` (`internal/app/openbook/openbook.go`) changes the state inside
   `app.Update`.
3. `TextBook.Turn` (`internal/reading/textbook.go`) moves the position, asking the renderer for
   the chapter's pages.
4. `renderer.pagesLocked` calls `Book.Chapter` then `layout.Paginate`, once per chapter.
5. The repaint reaches `app.Draw`, which calls the reader's `DrawAndRefreshLocked`: the page is
   drawn with `Page.Draw`, then `pocketbook.Refresh` updates the panel.
6. Back in `TurnPage`, `Syncer.Schedule` will send the progress a few seconds later.

```sh
go doc ./internal/typesetting/layout
go test ./internal/ebook/epub -run 'TestOpen|TestChapter' -v
go test ./internal/typesetting/layout -run 'TestHyphenatedWord|TestLongWord' -v
go test ./internal/reading -run TestTurnPages -v
make emu-fake EMUFLAGS="-fake-type calibreweb"   # open an EPUB and turn pages
```

The showcase EPUB of the fake Calibre-Web has Arabic, Hebrew, Chinese and emphasis marks:
`make shots SCRIPT=emulator/scripts/calibreweb-showcase.txt EMUFLAGS="-fake-type calibreweb"`
saves the screenshots in `build/shots`.

**Ask yourself:** where does a chapter's layout run the first time you open the book, and where
on the next page turns?

Then follow **thread 3**, a download:

1. A tap on a book not on the reader calls `downloadqueue.EnqueueLocked`
   (`internal/app/downloadqueue/downloadqueue.go`). If the queue was idle, it starts
   `downloader` with `app.Go`.
2. `downloader` calls `Store.Download` (`internal/shelf/download.go`), which branches on the
   book's `Format`.
3. For page images, fetchers (`fetchLoop`) ask the server for pages, a few at a time, and
   preparers (`prepareLoop`, then `preparePage`) call `pageimage.Prepare` and write each `.pg4`
   with `writeFileAtomic`.
4. For an EPUB, `downloadReflowable` (`internal/shelf/prepare_epub.go`) fetches the file whole,
   builds its index and its cover.
5. `book.json` is written last; `downloader` records the result inside an `Update` and takes
   the next book.

```sh
go doc ./internal/shelf
go test ./internal/shelf -run TestDownloadPreparesPages -v
go test ./internal/progress -run 'TestMerge|TestSyncerSchedule' -v
go test ./internal/servers -run TestCompareTitles -v
make shots SCRIPT=emulator/scripts/mealie.txt EMUFLAGS="-fake-type mealie"
```

**Ask yourself:** `downloader` runs on its own goroutine. Find every place where it touches the
state, and check that each is inside `app.Update` ([Threads and locks](/app/locks) says why).

## Part 5: a first change

You have now read the code of each thread. A good first change is a small one that runs the
whole loop of [Making a change](/appendix/contributing):

- **Add a case to a test.** Add a title to `TestCompareTitles`
  (`internal/servers/sorting_test.go`), such as a French title with an article, and run it.
- **Write an emulator script.** Copy `emulator/scripts/smoke.txt`, take a `shot` of a screen you
  have read the code of, and run it with `make shots SCRIPT=…`.
- **Profile a page turn.** `make profile SCRIPT=emulator/scripts/calibreweb-epub.txt`, then
  open the CPU profile and find `Paginate` and `blend` in it ([Finding what is
  slow](/reference/profiling)).

When the change is real, `make verify` runs everything: the build, the linter, the tests, every
script, and the comparison of screenshots with the baseline.
